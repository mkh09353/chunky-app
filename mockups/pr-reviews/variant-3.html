You

Where does the relay client decide to give up reconnecting? I want to know if a transient 502 from the edge is treated as fatal.

Assistant

The decision lives in the relay transport's backoff loop, not in the session layer. It classifies the close reason first, then either schedules another attempt or surfaces a disconnect to the session. A 502 arrives as a transport-level failure with no close frame, so it currently falls into the same bucket as an auth rejection and stops the loop.

That is the bug then. Transient status codes should keep retrying with backoff.

Agreed. The cleanest fix is to split the classifier into fatal and retryable outcomes, and treat 502, 503 and 504 as retryable with the existing jittered backoff, capped at the current ceiling. Auth failures stay fatal so a bad token still fails fast instead of hammering the edge.
